# session_timeline

Журнал агентной сессии + рендеры из одного файла:

- `render text`: компактный дайджест для контекста агента;
- `render html`: самодостаточный HTML-монолит для человека (без внешних зависимостей, работает офлайн);
- `render sqlite`: нормализованная база с представлениями для SQL-аналитики, в одну базу можно складывать много сессий.

Только stdlib Python 3.10+. Файлы:

| файл | назначение |
|---|---|
| `timeline.py` | CLI, модель, текстовый, HTML- и SQLite-рендеры, импорт |
| `template.html` | шаблон страницы сессии |
| `gui.py`, `gui.html` | Timeline Explorer: просмотр всех баз в браузере |
| `theme.css` | **общая дизайн-система** обоих экранов |
| `assets/logo.svg` | логотип inslopnia |

## Дизайн и как его менять

Концепция — «ночная смена»: тёмная тема с янтарным акцентом из логотипа плюс светлая «рассветная». Обе темы полноценные, переключатель ◐ запоминает выбор. Заголовки набраны узким шрифтом в духе вордмарка, время и числа — моноширинным. Декора минимум: без фоновых звёзд, зерна и свечений, каждая цифра показана один раз.

Весь внешний вид задаётся в `theme.css`. Рендерер и GUI встраивают его, логотип и favicon при сборке (`timeline.apply_brand`), поэтому результат остаётся одним файлом, а менять стиль нужно в одном месте:

- **шрифты:** `--font-ui`, `--font-display`, `--font-mono`;
- **поверхности и текст:** `--page`, `--surface*`, `--ink*`, `--muted`, отдельно для ночи и рассвета;
- **акцент:** `--accent*` (янтарь логотипа). Например, `#4fd1c5` даст бирюзовую ночь;
- **цвета данных:** `--c-*` — категориальная палитра в проверенном порядке (CVD-safe), статусы `--good`, `--warning`, `--serious`, `--critical`;
- **форма:** `--radius*`, `--shadow*`.

Стили, специфичные для страницы, лежат в `<style>` самих `template.html` и `gui.html`. Они используют только токены, так что смена темы на них распространяется автоматически.

## Модель данных

Append-only JSONL: одна запись на строку, у каждой есть `type` и `t` (epoch). Состояние восстанавливается сворачиванием всех записей, поэтому журнал можно дописывать параллельно и без блокировок.

| type | назначение |
|---|---|
| `session` | заголовок, задача, цель, `meta` (модель, конфиг…) |
| `agent` | объявление агента (`role` P/E/R/C/operator/runtime, `model`, `parent`) и `--start/--stop` интервалы активности |
| `event` | событие агента: `kind` (action, observation, decision, hypothesis, milestone, message, result, tool, error, note), `step` — привязка к узлу DAG, `to` — адресат (стрелка), `tokens`, `cost`, `refs`, `tags` |
| `dag` | `add`, `update`, `status`, `remove`, `dep_add`, `dep_rm`; `by` — кто сделал правку, `assignee` — кто исполняет узел |
| `usage` | расход токенов: дельта или `--cumulative` (нарастающий итог агента); in/out/cache/cost |
| `hyp` | гипотезы: open, testing, confirmed, refuted, abandoned + evidence |
| `incident` | баги и инциденты: severity, category, impact, workaround; `update`, `mitigate` (обошли, причина осталась), `resolve` (причина устранена) |
| `flag` | кандидаты флага: candidate, submitted, accepted, rejected |
| `outcome` | вердикт: solved, unsolved, partial, in_progress, abandoned (поддерживает `--task` для нескольких задач) |
| `phase` | именованные фазы (recon, exploit…), отображаются полосами |

Агент, которого ещё не объявили, создаётся автоматически. Роль угадывается по id: `P`, `E:<step>`, `R:<step>`, `operator`, `runtime`.

## Время (`--t`)

`now` (по умолчанию), `+12m`, `+1h5m30s`, `+mm:ss` / `T+mm:ss` / `T+h:mm:ss` (от начала сессии — формат можно копировать прямо из `render text` и `transcript`), epoch, ISO-8601, `HH:MM[:SS]`.

Запись раньше старта сессии или в будущем даёт предупреждение; `validate` такие места перечисляет.

## Шпаргалка для агента

```bash
export TIMELINE_FILE=runs/my-task/timeline.jsonl     # или -f <file> перед командой
T="python C:/Users/Duhamster/Prog/insomnia/session_timeline/timeline.py"

$T init "CTF Cup / pwn / heap" --task heap --goal "ctfcup{...}" --meta model=glm-5.3
$T agent P --role P --model zai/glm-5.3 --start
$T dag add recon -o "разведка" --assignee E:recon            # by=P по умолчанию
$T dag add exploit -o "эксплойт" --deps recon --assignee E:exploit
$T dag status recon running
$T event E:recon "UAF в delete_note" -k milestone -s recon --to P --tokens 41000
$T hyp add "UAF в delete_note" -a P                           # → H1
$T hyp set H1 confirmed -e "show() после free печатает fd"
$T dag status recon done --by runtime
$T dag update exploit -o "UAF→FSOP" --note "нет __free_hook"
$T dag dep-add exploit leak     |  $T dag remove cleanup -r "не нужно"
$T tokens E:recon 140000 --cumulative --cost 0.21
$T incident add "stdout pi теряет финальное событие" --sev high -c harness -s recon --workaround "читать pi-sessions"   # → I1
$T incident mitigate I1 --note "обошли чтением pi-sessions"  # баг остался → не resolve
$T incident resolve I1 --note "исправлено в харнессе"
$T flag "ctfcup{...}" --status accepted -a E:exploit
$T outcome solved --flag "ctfcup{...}" --summary "UAF → FSOP"
$T agent P --stop --status done

$T render text                                  # всё
$T render text --sections summary,dag,incidents --detail 0
$T render text --last 20 --agent E:exploit      # хвост ленты по агенту
$T render text --kinds milestone,decision,error --since +30m
$T render html -o report.html
$T validate [--strict]                          # ERROR → exit 1; WARN — вероятные огрехи аннотации

# компактное чтение переписок pi с T+ ЭТОГО журнала (≈10× меньше сырых jsonl)
$T transcript run/pi-sessions/*_planner-run.jsonl -g 'work|notes'
$T transcript run/pi-sessions/*_e-recon-r0.jsonl --since +30m --until +35m --results 0
$T transcript run/pi-sessions/*.jsonl --last 40 --thinking
```

## Правила аннотирования (для агента)

1. **Сначала скелет, потом смысл.** Для прогона харнесса начните с `import-harness`, затем дописывайте только то, чего нет в ledger: решения, находки, гипотезы, инциденты, фазы.
2. **Время — из источника.** Берите T+ из `transcript` и передавайте в `--t T+mm:ss`. Не используйте `now`, когда разбираете прошлое.
3. **Находки адресуйте.** Если milestone или result исполнителя ушёл планировщику, ставьте `--to P`: так в HTML появляется стрелка отчёта. Решение P про шаг: `-s <step>`, при поручении — `--to E:<step>`.
4. **Гипотезы:** `hyp add` в момент появления, `hyp set` с `-e` (на чём основано) в момент проверки. `confirmed`/`refuted` без evidence `validate` отметит.
5. **Категория инцидента:**

   | категория | что относить |
   |---|---|
   | `harness` | ошибка кода runtime (watchdog, потеря stdout, лиз) |
   | `orchestration` | решения P и устройство DAG: поздний параллелизм, монолитный шаг, неверный acceptance |
   | `agent` | поведение исполнителя: зацикливание, побочные эффекты, игнор указаний |
   | `model`, `infra`, `env`, `tooling`, `platform`, `other` | по смыслу |

6. **`mitigate` ≠ `resolve`.** Если проблему в сессии обошли, а причина осталась, это `mitigate`. Открытыми считаются только `open` и `investigating`.
7. **Не перегружайте контекст.** Читайте `transcript` с `-g`, `--since/--until`, `--last`, а не сырые jsonl. Свой журнал смотрите через `render text --sections … --detail 0`.
8. Перед рендером запустите `validate`: ошибок быть не должно, предупреждения разберите.

Каждая команда печатает id созданной записи (`H1`, `I2`, `e7`…), на него можно сослаться через `--refs`.

## SQLite-рендер

```bash
$T render sqlite                                   # → <journal>.db, session_id = имя файла журнала
$T -f a.jsonl render sqlite -o all.db              # несколько сессий в одну базу
$T -f b.jsonl render sqlite -o all.db --session-id run-b
$T render sqlite -o all.db --fresh                 # пересоздать файл базы
```

Перерендер той же сессии заменяет только её строки, остальные сессии в базе сохраняются. Поэтому одна база может хранить много прогонов для сравнения.

**Таблицы.** У каждой есть `session_id`; в событийных таблицах есть `t` (epoch) и `t_rel` (секунды от старта сессии).

| таблица | содержимое |
|---|---|
| `sessions` | итог сессии: вердикт, флаг, длительность, токены (in/out/cache), стоимость, счётчики узлов, инцидентов, гипотез, `meta_json` |
| `agents`, `agent_spans` | агенты с итогами по токенам и стоимости, интервалы активности |
| `nodes`, `node_deps`, `node_runs` | финальный DAG, рёбра, каждая попытка выполнения узла с длительностью |
| `dag_ops` | вся история правок DAG: `by_agent`, `prev_status` → `status` |
| `events` | лента событий: `agent` → `to_agent`, `kind`, `step` |
| `usage` | расход токенов с ролью агента |
| `hypotheses`, `hyp_history` | гипотезы и смена их статусов |
| `incidents`, `incident_history` | инциденты; `time_to_resolve_s`, `auto` — признак автоинцидента импорта |
| `flags`, `outcomes`, `phases` | флаги, вердикты, фазы |
| `records` | сырые записи журнала (JSON) — для полного восстановления |

**Представления.**

| представление | что показывает |
|---|---|
| `v_sessions_compare` | сравнение прогонов: вердикт, минуты, токены, $, узлы, инциденты, время до принятого флага |
| `v_timeline` | события и правки DAG в одной ленте с `T+hh:mm:ss` |
| `v_agent_share` | доля агента в токенах и стоимости, токены за минуту активности |
| `v_role_totals` | итоги по ролям P/E/R/… |
| `v_node_summary` | по узлам: эффективный статус, время выполнения, события, токены и $ шага, инциденты |
| `v_tokens_per_minute` | расход по минутам и ролям |
| `v_open_incidents` | открытые инциденты, отсортированные по важности |

### Рендер обратно из базы

Сгенерированная база может служить источником для любого рендера. Сессия восстанавливается из таблицы `records` без потерь: модель, текст и HTML побайтно совпадают с рендером из исходного JSONL.

```bash
$T -f all.db sessions                                  # список сессий в базе
$T -f all.db --session demo render html                # → all.demo.html
$T -f all.db --session demo render text --sections summary,incidents
$T -f all.db --session demo render sqlite -o other.db  # перенести сессию в другую базу
$T -f all.db --session demo render jsonl -o demo.jsonl # восстановить журнал
```

`--session` нужен, только если в базе больше одной сессии. Как источник база доступна только для чтения. Чтобы дописывать события, сначала восстановите журнал командой `render jsonl`.

```sql
SELECT * FROM v_sessions_compare;
SELECT node_id, status, run_s, tokens, cost FROM v_node_summary WHERE session_id='demo';
SELECT t_plus, agent, kind, title FROM v_timeline WHERE session_id='demo' AND kind IN ('milestone','error','dag_status');
```

## Импорт из прогона inslopnia_harness

```bash
$T -f t.jsonl import-harness ../harness_experiments/ctf-runs/<task>/run [--bucket 60]
$T -f t.jsonl import-harness <run> --merge   # переимпорт с сохранением ручных аннотаций
```

Что берётся из `ledger.sqlite3`:

- `step_added`, `step_updated`, `step_started`, `step_done`, `step_failed`, `step_cancelled` → правки и статусы DAG (`by`: planner/operator/runtime);
- `step_report`, `executor_answer`, `exec_directive`, `operator_*` → события и сообщения со стрелками;
- `step_failed`, `stale_*_killed` и аварийный `planner_turn_end` → автоматические инциденты;
- `run_finished` → вердикт и флаг (из строки `FLAG:`).

Токены и стоимость берутся из `pi-sessions/*.jsonl` (`usage` ассистентских сообщений) и агрегируются по агентам с бакетом `--bucket` секунд. Именно эти данные, а не `step_progress`, служат источником: stdout pi на Windows иногда теряется. После импорта агент дописывает в журнал гипотезы, инциденты и решения.

## Что показывает HTML

- **Шапка:** заголовок, вердикт, одна строка «задача · модель · время», пять KPI (длительность, токены и стоимость, узлы DAG, инциденты, гипотезы), флаг и резюме. Детали (in/out/cache, фазы) — во всплывающих подсказках.
- **Таймлайн-дорожки:** по одной на агента. Полосы активности окрашены статусом узла (выполняется, готово, провал, отменён). Внутри дорожек — маркеры событий, у каждого типа своя форма; чипы типов над таймлайном скрывают и показывают их. Роль агента подписана бейджем на дорожке, токены и стоимость — под именем, модель и время активности — в подсказке. Ромбы — правки DAG на дорожке автора правки. Пунктирные кривые P→E показывают поручения, старты и отмены, то есть связь оркестрации с исполнением. Отдельно показаны стрелки сообщений и полосы фаз.
- Под дорожками на общей оси два графика: накопленные токены стеком по ролям и прогресс DAG (число узлов по статусам).
- **DAG со скраббером:** состояние графа в момент курсора. Узлы, которые ещё не добавлены, показаны пунктирными «призраками»; последний изменённый узел обведён. Статус написан в самом узле. Рядом список ревизий; доступны ◀ ▶ и ▶ play.
- Курсор общий: клик по таймлайну, ревизии, инциденту или строке журнала переносит его, и DAG перерисовывается. Клик по агенту или узлу включает фокус на шаге: всё постороннее приглушается.
- Ниже: карточки инцидентов (важность, категория, статус, заголовок, 2 строки описания; влияние, обход и история — в боковой панели) и гипотез, журнал событий с поиском и фильтрами, боковая панель с подробностями (Esc закрывает).
- Кнопки таймлайна (связи, − / Fit / +, снять фокус) стоят в его заголовке; масштаб ещё и Ctrl+колесо.

## GUI: Timeline Explorer

```bash
python gui.py [<папка|файл> …] [--port 8780] [--open]
# пример: python gui.py ../harness_experiments/timelines examples --open
# пример: python gui.py ../harness_experiments/ctf-runs/codex/run    # один прогон харнесса
```

`gui.html` — одностраничный монолит (разметка, стили и JS в одном файле). `gui.py` — локальный сервер на stdlib, слушает только `127.0.0.1`. Он рекурсивно ищет в указанных папках `.db`, созданные `render sqlite`, и **рендерит их самим `timeline.py`**, импортированным как модуль: HTML-таймлайн, текст, `validate`, выгрузку `jsonl`. Отдельной копии рендера нет, поэтому любое улучшение утилиты сразу видно в GUI.

| раздел | что показывает |
|---|---|
| Обзор | сводные цифры и сортируемая таблица всех сессий из всех баз; клик открывает сессию. Открывается пунктом «Обзор» вверху боковой панели или кликом по логотипу |
| Таймлайн | HTML-рендер утилиты во фрейме (без повторного заголовка и вердикта — они в шапке GUI); меню «⤓ экспорт»: новая вкладка, HTML, JSONL |
| Текст | `render text` с выбором секций и детализации |
| Анализ | `ANALYSIS.md`, лежащий рядом с базой; вкладка есть, только если файл есть |
| Проверка | `validate`: ERROR и WARN |
| SQL | запросы только на чтение к базе; пресеты по представлениям; `:s` = текущая сессия; Ctrl+Enter |

Состояние открытой вкладки хранится в URL (`#db=…&s=…&tab=…`). Индекс пересканируется раз в 30 с и по кнопке ⟳. Запросы к базам вне открытых источников отклоняются.

### Открыть папку или файл из GUI

Кнопка с папкой в шапке (или **Ctrl+O**) открывает диалог источников. Режим сверху: **«Открыть вместо текущих»** заменяет список источников, **«Добавить к текущим»** дописывает в него.

| способ | что делает |
|---|---|
| поле пути | вставьте путь к папке или файлу и нажмите Enter; кавычки от «Копировать как путь» можно оставить |
| обзор (справа) | браузер файловой системы через сервер: диски, «домашняя», «рабочая», папки запуска, хлебные крошки. Подпапки помечены «есть .db» или «прогон харнесса», а у файлов таймлайнов показаны тип и число сессий. Кнопка «Открыть эту папку» стоит в панели над списком, «Открыть»/«Добавить» — у каждого файла; двойной клик открывает |
| системный диалог | «Папка…» / «Файл…» — стандартное окно ОС (tkinter в дочернем процессе, без tkinter кнопок нет) |
| перетаскивание | бросьте файл или папку в окно (вне диалога — всегда «добавить»), либо «выбрать файлы / папку» в диалоге. Браузер не сообщает настоящий путь, поэтому на сервер уходит **копия** в `%TEMP%/timeline-gui/uploads` без живого обновления; при перезапуске копии удаляются |
| недавние | последние 10 открытых путей (хранятся в `localStorage` браузера) |

Что считается таймлайном:

- **папка** сканируется рекурсивно на БД `render sqlite` (пропускаются `workspace`, `sessions`, `pi-sessions`, скрытые папки; не больше 20 000 папок);
- **файл** — БД `render sqlite`, JSONL-журнал `timeline.py` или `ledger.sqlite3` харнесса. Журнал и ledger рендерятся на лету (`render sqlite` / `import-harness`) в кэш `%TEMP%/timeline-gui/derived` и перестраиваются, когда меняются mtime и размер файла (у ledger учитывается и `-wal`), поэтому идущий прогон обновляется сам;
- **папка прогона харнесса** (в ней лежит `ledger.sqlite3`) открывается как этот прогон;
- **папка с прогонами** (например, `ctf-runs/`): если таймлайн-БД в ней нет, а `ledger.sqlite3` есть, прогоны импортируются автоматически. Чтобы импортировать их и рядом с БД, нажмите «+ N прогонов харнесса» у источника в диалоге.

Одна и та же сессия из разных файлов (например, `timeline.db` и `ledger.sqlite3` того же прогона) показывается один раз, а файл-источник выбирается в шапке сессии. Если источников несколько, в боковой панели появляется фильтр по источнику. «Обзор» и график инцидентов учитывают этот фильтр.

Сервер может открыть любой путь на машине, поэтому отвечает только на `Host` = `127.0.0.1` / `localhost` (защита от DNS rebinding). POST-запросы принимаются только со своего `Origin` и с `Content-Type` JSON или octet-stream: обычная HTML-форма с чужого сайта так не отправит (CSRF).
